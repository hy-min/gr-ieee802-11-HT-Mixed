## Task 2: 分析 H52 为零的根本原因

**Files:**
- Analyze: `lib/frame_equalizer_impl.cc`
- Test: 运行测试分析输出

**可能原因:**

1. **kLltf48TX 与实际 TX 不匹配**
   - TX 发送的 L-LTF 可能有不同的幅度或相位
   - 需要检查 TX 端 L-LTF 的生成方式

2. **子载波索引对应错误**
   - `d_early_eqsym[0][i]` 对应 `kHeader48Sc[i]` 顺序
   - `kLltf48TX[i]` 也是 `kHeader48Sc` 顺序
   - 索引应该正确，但需要验证

3. **LTF0 和 LTF1 完全相同**
   - IEEE 802.11 定义 LTF0 和 LTF1 应该是不同的（后者有符号翻转）
   - 如果完全相同，说明 TX 或 RX 处理有问题

**Steps:**

- [ ] **Step 1: 检查 TX L-LTF 生成方式**

```bash
grep -n "generate_l_sig_header\|LTF\|lltf\|L-LTF" /home/hy/gr-ieee802-11/lib/signal_field_impl.cc | head -30
```

- [ ] **Step 2: 检查 LTF0 和 LTF1 的预期差异**

IEEE 802.11-2016:
- L-LTF 是两个连续的 OFDM 符号
- 第二个符号（LTF1）是第一个的复共轭（用于信道估计）
- 但 `extract_header52_from_sym64` 提取的是 FFT 输出，两个符号可能相同

- [ ] **Step 3: 验证 RX 接收的 LTF0 和 LTF1 是否有相位差异**

从 Task 1 的 H52_DIAG 输出检查：
- `lltf0_52[i]` 和 `lltf1_52[i]` 应该是共轭关系
- 如果完全相同，说明 RX 没有正确区分两个符号
