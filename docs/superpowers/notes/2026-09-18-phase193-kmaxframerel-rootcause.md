# Phase 193: 长帧全灭的根因 —— `kMaxFrameRel = 128` 硬上限（2026-09-18）

**类型：根因定位 + 修复 + 验证**

## 一句话

**`lib/frame_equalizer_impl.cc:60` 的 `kMaxFrameRel = 128` 是每帧符号槽位的硬上限；
`d_sym_idx > 128` 时均衡器直接丢弃整帧。** 该常量自早期设定后从未被逼近——
**项目从 P31 至今全部实验都用 `--len 38`（7+21 = 28 槽），离 128 有 4 倍余量**——
直到 P192 第一次扫描帧长才撞上它。

## 证据链（三重独立、互相印证）

### ① 尖锐的位置预测

`ceil((16 + 8×(len+28) + 6) / 26)` 给出帧所需的数据符号数；`d_sym_idx` 从 7（`kDataStartRel`）开始。
若上限是 128，则边界必须落在需要超过 128 的第一档：

| len | 帧需符号 | 需 `sym` 到 | 实测 `EQ_EMIT` | 实测 `max_sym` | 结果 |
|---|---|---|---|---|---|
| 200 | 71 | 77 | 71（完整）| 77 | ✅ OK=1 |
| 350 | 118 | 124 | 118（完整）| 124 | ✅ OK=1 |
| **380** | **127** | **133** | **122** | **128** | ❌ OK=0 |
| 400 | 133 | 139 | 122 | 128 | ❌ OK=0 |

**`d_sym_idx` 精确停在 128。** 350 需要到 124 ⇒ 通过；380 需要到 133 ⇒ 卡住。

**由 128 反推的最大 payload = 365 字节**（`(128-7)×26/8 = 393` PSDU）⇒ 边界必须落在 (350, 380) 之间 —— **实测正是如此**。

### ② 判定日志实际出现

```
len200  "[EQ_FRAME_END] max frame exceeded" = 0  → 通过
len350  0                                        → 通过
len380  1   (sym_idx=129)                        → 失败
len400  1                                        → 失败
```

### ③ 代码路径

```c
// lib/frame_equalizer_impl.cc:60
static constexpr int kMaxFrameRel = 128;

// 10103
if (d_in_frame && d_sym_idx > kMaxFrameRel) {
    USRP_LOG("[EQ_FRAME_END] max frame exceeded sym_idx=%d\n", d_sym_idx);
    reset_frame_state();
    d_discard_until_wifi_start = true;      // ← 整帧丢弃
}
```

## 这个常量解释了本次调查中每一个悬而未决的现象

| 先前观测 | 归因 |
|---|---|
| 干净自链路 len≥400 全灭（P192）| 帧需 > 128 槽，被整帧丢弃 |
| len200 正常 / len400 失败 | 71 vs 133 符号 |
| 失败率随长度单调上升 | 越界幅度递增 |
| **"固定字节 394"**（P193 早期结论）| 丢弃前最后一个符号的边界，**不是固定位置** |
| **`full_syms=122` 反复出现** | **122 = 128 − 7 + 1 = 上限本身** |
| 头部正确、尾部错误 | 越界发生在帧尾 |
| `[decode_mac][COMPLETE]` 后无 PDU | 均衡器已丢弃该帧，下游拿到的是残段 |

## 修复

```c
static constexpr int kMaxFrameRel = 480;
```

**推导（不猜）**：`MAX_PAYLOAD_SIZE 1500 → MAX_PSDU_SIZE 1528
→ ceil((16 + 8×1528 + 6)/26) = 471` 数据符号（MCS0 最密，26 data bits/符号）
`+ kDataStartRel(7) = 478`，取 **480** 留余量。

**动手前的尽职检查**（防止抬高上限变成越界写）：
- `kMaxFrameRel` 全文件**只有 2 处引用**：定义 + 判界。**没有任何分配依赖它**
- 文件中所有 `[128]` 数组都是 `char buf[128]` —— **日志字符串缓冲**，与符号无关
- `d_frame_symbols` 由编码比特数**动态计算**；`path_data` 动态分配 ✓

**USRP 复现验证**（按铁律"离线正收益 ≠ 实时正收益"）：

```
len400:  FCS_OK=401/750 = 53.5%   win=[77, 81, 83, 80, 80]     修复前 = 0.0%
len1000: FCS_OK=578/750 = 77.1%   win=[117, 125, 126, 119, 91]  修复前 = 0.0%
```

**两个此前 0% 的长度都转为可用。** 53.5% / 77.1% 而非 100% 是合理的：
USRP 有 RF 噪声，长帧累积的符号差错更多；**离线无噪声回环在同长度是 100%**。
两者一致——**结构性丢弃已消除，剩下的是自然误码率**。

## 方法学教训（本 phase 最贵的部分）

### 1. 我应该第一步就跑离线回环

P192 用 USRP 扫了 6 个长度、P193 又跑了两轮，才想到**项目自带一个纯软件的 PHY 回环**。
铁律写着"**先合成后 USRP**"——**回环 10 秒一次、确定性、可开任何 dump**，本该是第一站。
代价：约两轮设备时间。

### 2. 我反复把"仪表形态"当成"物理结论"

本 phase 我提出并随后**自行撤回**了两个根因：
- **"发射机截断最后 11 个符号"** ← 实为 `stop()` 生命周期钩子打印的 `where=stop`
- **"固定字节 394"** ← 实为丢弃边界

两次都是**读代码之前就采信了计数**。第三次才成立（kMaxFrameRel），
而它成立恰恰是因为**代码、日志、位置预测三者独立吻合**。

### 3. 数行 ≠ 读行

`[EQ_EMIT] sym=%d/%d` 的分母、`[FAIL_PSDU]` 的 66 字节上限、
`[decode_mac][INCOMPLETE]` 的 `where=` 字段——**我都是先数了行数、后读的内容**，
而每次读内容都推翻了我从行数得出的推断。
