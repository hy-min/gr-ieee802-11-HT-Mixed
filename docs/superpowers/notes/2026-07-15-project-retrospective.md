# 阶段性反思总结：gr-ieee802-11 USRP Realtime FCS_OK 攻关

**日期：** 2026-07-15
**作者：** Claude（基于 163 篇项目记忆 + Phase 41–147 完整攻关史）
**范围：** 从"30+ REFUTED 均衡器墙"到"管线打通 + 段错误修复"的方法论复盘

---

## 一、项目概况

**目标（用户的绝对约束）：** 实现 USRP realtime FCS_OK —— X310 + UBX-160 硬件
端到端、空口路径逐帧成功。用户明确拒绝"现状/止损/closure"作为终态
（2026-07-07：*"不可能接受现状，我的目标是实现USRP FCS OK"*）。

**时间跨度：** 数月，其中 2026-06-24 ~ 07-15 为高强度密集攻关（22 天内产生
~140 份 verdict 文档，单日峰值 22 份）。

**当前状态（Phase 147 后）：**
- RX 解码器**被证明正确**（离线漏斗 decode_mac 级 FCS 率 81%）。
- 实时管线**已打通**（Phase 146 修复 GNU Radio 调度 stall）。
- 实时段错误**已修复**（Phase 147 sync_short 跨实例竞争）。
- USRP 实时 **FCS_OK = 46/45s 稳定无崩溃**（对比 Phase 146 的 2/30s）。

## 二、三个真正的突破，以及它们共同揭示的真相

| 突破 | Phase | 本质 | 教训 |
|---|---|---|---|
| 解码器被证明正确 | 145c | file-replay FCS_OK=5 | "能解码"与"帧能送达解码器"是两回事 |
| 实时管线打通 | 146 | 阻塞是 GNU Radio 调度 stall（空闲 TX 路径 `ofdm_cyclic_prefixer` tag 饥饿，拖慢 5000×） | 真正的瓶颈在**结构**，不在算法 |
| 实时段错误修复 | 147 | "低 FCS"是 `sync_short` 跨实例 `static` 竞争崩溃（Heisenbug），不是解码器 | 崩溃点 ≠ 根因点；对工具（ASan）才能抓到 |

**共同揭示的真相：** 这个项目的困难**从来不是"解码器/均衡器不行"**。三个
最大的进展全部来自**重新定位"真正的瓶颈在哪一层"**，而不是在原有层上继续
优化。解码器早就好了；问题是帧**到不了**解码器（调度 stall、段错误、同步）。

---

## 三、最深刻的元教训（Meta-Lessons）

### 教训 1：先根因后修复（Iron Law）—— 以及违反它的代价

> systematic-debugging 的第一原则：**没有找到根因之前，不允许提修复。**

本项目最大的时间黑洞是 **100+ 个 phase 反复攻击均衡器层**（2-way/Wiener/DDE/
跨帧/频域低通…30+ 到 100+ REFUTED），全部基于一个**症状**（USRP FCS 低）。而
真正的根因是**三个与均衡器无关的问题**：调度 stall（146）、段错误竞争（147）、
上游同步。这三者**没有一个是均衡器问题**。

**代价：** 大量精心设计的均衡器方案（每一个都"理论上能降 σ"）在错误的层上
被反复 REFUTED。这些工作并非毫无价值（排除了假设、建立了基线），但**如果
早做根因定位（像 146/147 那样），可以少走非常多弯路。**

**应用：** 每次"卡住"时，先问一句——*我是不是又在攻击一个症状，而不是根因？
真正的瓶颈在这一层吗？*

### 教训 2：区分"算法正确"与"管线送达"

解码器在 loopback、file-replay 下**反复被证明正确**（FCS_OK）。但实时就是不出
FCS_OK。很长一段时间里，这被解读为"实时信号太差 → 解码器扛不住"，于是继续
攻解码器。**这是错误的归因。**

正确的拆解是：
- **算法正确性**（给定一帧 IQ，能否解码）—— ✅ 早已解决。
- **管线送达**（实时中，帧能否完整、准时地送达解码器）—— ❌ 这才是瓶颈
  （stall、crash、同步、欠载）。

**应用：** 当"离线能、实时不能"时，**不要怀疑算法，去查送达链路**（调度、
缓冲、时序、并发、硬件流）。这是本项目最值钱的认知之一。

### 教训 3：一个真实的物理极限会变成"替罪羊"，掩盖其它可修的问题

Phase 112 R1 确认的 **1.77 rad per-SC 相位噪声底是真实的**（USRP 模拟链物理
噪声）。但它后来变成了一种"习得性无助"——**所有失败都被归因于它**，仿佛
"反正都是噪声的锅"。

事实是：1.77 rad 限制的是 **per-frame 解码成功率**（decode_mac 级 ~64%），
它**根本不能解释**"帧到不了解码器"（stall/crash/同步）。把一个真实但**局部**
的极限，当成**所有**问题的挡箭牌，是本项目拖延的重要原因。

**应用：** 承认一个真实极限的存在，但**不要让它成为停止排查其它层的理由**。
"这是物理极限"和"这是可修的 bug"可以同时存在于不同层。

### 教训 4：坚持目标 ≠ 坚持某一层

用户的"不可能接受现状"是**对的**，并最终推动了突破。但执行中，这份坚持一度
被**窄化为"坚持攻击均衡器层"**。真正的坚持应该是**对目标的坚持**，配上
**对"哪一层是真瓶颈"的不断重新审视**。

**应用：** 目标层面不妥协（USRP realtime FCS_OK），但**战术层面保持流动性**
——敢于说"这一层我已经攻得够多了，瓶颈在别处"。closure 不可接受，但
"换一层攻"不是 closure。

### 教训 5：Heisenbug 需要对的工具，且崩溃点往往 ≠ 根因点

Phase 147 的段错误是典型 Heisenbug：gdb 下不崩、libSegFault 下不崩、间歇性、
时序相关。**第一次 gdb backtrace 指向 `mac_impl::app_in`——那是"受害者"**
（堆破坏后在下次 pmt 分配时崩），不是根因。真正的根因（`sync_short` 的
`static sorted_buf` 跨实例 `std::sort` 竞争）是 **ASan 实时运行**才抓到的。

**应用：**
- 堆破坏型 Heisenbug，**崩溃现场 ≠ 作案现场**。
- 工具链优先级：**AddressSanitizer > gdb backtrace > 日志**。ASan 在 OOB 写
  **发生的当下**报错，而不是在受害者倒下时。
- **合成复现**（`p147_race_repro.py`：双实例噪声源）能把 Heisenbug 变成
  可 TDD 的确定性测试——先红后绿。

### 教训 6：不要相信任何单一的中间指标

- `LSIG_DECODE OK = 695` 看着像"L-SIG 大量成功"，实际是**大量假阳性**
  （len=779/3427 等垃圾长度）——它**不能用作漏斗的一级**。
- `FCS_OK = 2`（Phase 146）看着像"实时只能解 2 帧"，实际是**段错误早杀 +
  消息队列漏计**——真实值是 46。

**应用：** 关键计数要有 **ground-truth 对照**（如 decode_mac 的 C++ stderr
`DECODE_SUCCESS`，不可被消息队列丢弃）。对任何"计数"，先问"它可能被什么
污染/漏计"。

### 教训 7：函数级 `static` 可变缓冲 = 跨实例竞争（具体 C++ 教训）

`sync_short.cc:124` 的 `static float sorted_buf[4096]` 被**两个 sync_short
实例**（wifi_phy_hier RX 路径 + RX-only 链）在不同 GNU Radio 线程上并发
`memcpy`/`std::sort` → 越界崩溃。

**应用（可复用规则）：** 任何**多实例块**里的**函数级 `static` 可变缓冲**，
都是跨实例竞争。scratch buffer 一律用**栈私有**或**成员变量**。离线单实例
测试**永远测不出**这类 bug——必须用**双实例合成**或**ASan 实时**。

## 四、方法论：什么有效 vs 什么无效

### ✅ 有效（应继续保持）

| 方法 | 证据 |
|---|---|
| **systematic-debugging（先根因）** | 146/147 两个突破都来自它 |
| **AddressSanitizer** | 精确定位 Heisenbug 的 OOB 源头 |
| **TDD 合成复现** | 双实例 race repro，红→绿 |
| **离线漏斗分析** | 一次性看清"帧在哪一级掉" |
| **file-replay 隔离** | 把"算法正确性"与"UHD 流"解耦 |
| **记忆文件 + verdict** | 163 篇，跨会话连续性全靠它 |
| **单变量改动** | 每个可复现的 REFUTED/PASS 都靠它 |

### ❌ 无效（应避免）

| 反模式 | 后果 |
|---|---|
| **同层反复微调**（均衡器 100+ 次） | 撞在错误层的天花板 |
| **不质疑"哪一层是真瓶颈"** | 把物理极限当替罪羊 |
| **凭感觉选架构**（DD/Kalman/Wiener 轮着试） | 每个都 REFUTED，没有根因支撑 |
| **把"离线能"当"实时也能"** | 忽略了送达链路 |
| **把单一日志行当漏斗指标** | 假阳性/漏计误导方向 |
| **Heisenbug 只用 gdb 调** | 崩溃被调试器掩盖 |

## 五、对后续工作的指导原则

1. **主战场已转移**：解码器/均衡器**不再是瓶颈**。真正剩余的是
   **decode_mac 到达率**（目前 ~10% 整体，多数帧没到 decode_mac）和
   **per-frame 成功率**（~64%，1.77 rad 噪声）。这两者**现在可以在持续、
   稳定的实时环境下测量和攻击**（不再被 stall/crash 掩盖）。

2. **每次"卡住"先做层间定位**：写下当前漏斗（发送→同步→L-SIG→HT-SIG→
   decode_mac→FCS），找**跌幅最大的一级**，只攻那一级。不要默认"又是均衡器"。

3. **保持 file-replay 回归**作为正确性基线（loopback 3/3 PASS），但**任何
   结论必须落到 USRP 实时**才算数。

4. **单变量 + 可复现 + 先合成后硬件**：新假设先在合成/离线验证，再上 USRP
   （省 cable budget，也避免硬件状态污染结论）。

5. **工具箱**：Heisenbug/崩溃 → ASan 优先；竞态 → 双实例合成复现；
   计数 → C++ stderr ground-truth 对照消息队列。

6. **硬件卫生**：USRP RFNoC 崩溃后会进入坏状态（`uhd_usrp_probe` nudge 恢复，
   必要时 power cycle）。CPU governor 应切 performance（需 sudo）。cable
   budget 谨慎使用。

---

## 六、结语

这个项目最难的部分，**从来不是让解码器变得更强**——它早就够强了。最难的是
**一次次诚实地区分"症状"与"根因"、"这一层"与"那一层"、"物理极限"与"可修的
bug"**。

三个突破（145c/146/147）没有一个是靠"更聪明的均衡器"取得的，全部来自
**换一个角度看问题**：解码器没问题 → 是送达问题；实时低 FCS → 是崩溃问题；
崩溃在 mac → 不，根因在 sync_short。

> **目标坚定不移（USRP realtime FCS_OK），但对"瓶颈在哪一层"保持永恒的
> 重新质询。这，是这个项目用 100+ 个 phase 换来的最宝贵经验。**

## 附：关键事实锚点

- **解码器正确性**：离线漏斗 decode_mac 级 FCS 率 81%（21/26），全部 len=66。
- **Phase 146 根因**：`wifi_phy_hier` 空闲 TX 路径 `ofdm_cyclic_prefixer` tag
  饥饿 → GNU Radio 调度 stall ~5000×。修复 = RX-only 链。
- **Phase 147 根因**：`sync_short.cc:124` `static sorted_buf` 跨实例
  `std::sort` 竞争 → 崩溃。修复 = 栈私有缓冲。
- **修复效果**：USRP 实时 FCS_OK 2/30s（+ 50% 崩溃）→ **46/45s 零崩溃**。
- **1.77 rad 物理噪声底**：真实，但只影响 per-frame 解码成功率，**不是**
  "帧到不了解码器"的原因。
- **当前剩余攻击面**：decode_mac 到达率（~10%）+ per-frame 成功率（~64%）。
