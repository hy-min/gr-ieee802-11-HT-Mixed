## 3. 三个关键否定（全部逐帧证据）

1. **丢失帧与噪声无关**：13/15 丢失帧 ±100ms 内**零噪声 episode**（仅
   seq=2873 邻近 5 个、seq=308 邻近 1 个）。"噪声撞帧"机制（162b/163 的动机）
   **不解释清轮残余**——它只解释吵轮尾巴。这就是两个门控失败的原因之一：
   攻的不是清轮主损。
2. **丢失帧是满强度真帧**：丢失帧 episode max_cor = 643.7–675.6，与 OK 帧
   （min=636, p50=657）**不可区分**。不是弱帧。
3. **检测不是瓶颈**：0 检测损失（162b/163 已反复确认）。

## 4. 修正后的根因：两条具体尾巴

**尾巴 A（链损，8/3198 = 0.25%）**：满强度、已检测、无噪声的帧，死在
L-SIG/HT-SIG 对齐。sync_long 的 search_frame_start 计算出 d_frame_start
（实测散在 121–238）后**强制改写为 174**（`d_frame_start=X -> forcing to 174`，
本运行 3236 次强制 vs 3237 次提交）。该启发式对 99.75% 帧成立，但 ~0.25%
帧的真实帧起始不在 174 → FFT 窗错位 → L-SIG 垃圾（垃圾 L-SIG 156 次尝试）。
这是**真实缺陷**（frame-start 启发式的失败尾巴），非环境。

**尾巴 B（解码终败，7/3198 = 0.22%）**：P161 频带边缘衰落尾巴的软判决后
残余（P162 软 viterbi 已 −83%，这是剩下的深衰落实现）。

## 5. 与 162b/163 的关系

162b/163 攻的是"噪声→链污染"，但那是**吵轮尾巴**的机制，不是清轮主损。
两门控失败 = 攻错了目标人口。本次逐帧取证纠正了目标：**清轮残余 = 对齐尾巴
+ 衰落尾巴**，两者都是具体可攻的缺陷/物理尾巴，不是环境噪声。

## 6. 下一步选项（风险权衡，需用户定）

- **攻尾巴 A（sync_long 对齐）**：方向 = per-frame frame-start 精化（用
  L-LTF 相关峰而非强制常数 174，或修 L-STF 干扰致 lower_peak 偏移的根因）。
  风险：sync_long 是全 repo 最脆弱、100+ phase 历史的文件。需先加 commit

- 当前：静轮 ~99.5%，端到端清轮残余 0.47%（8 链 + 7 解码）。

## 7. 二次取证：链损机制精确定位（2026-08-10，p163d_fate.err）

加 sync_long 提交点位置仪表（commit 行带 computed_fs + tag_off）+
sync_short trigger 行带 out_pos（压缩→实时映射）后逐帧 join（0 未映射）：

- **全部 21 个丢失帧 = 无 commit（搜索未提交）**，不是"提交但错位"。
- 搜索一旦运行几乎必提交（3228/3229）；P133 S&C 门默认关，无关。
- OK 帧 commit 的 computed_fs 分布 p5=103/p50=213/p95=238（**测量值本身就
  远离 174**，强制到 174 反而对——因为压缩流时序使测量值系统性偏移）。

**机制**：满强度帧被检测、episode 被转发，但 sync_long 的 SYNC_LENGTH 窗口
搜索没有在其 L-LTF 上提交——压缩流上每个 episode 到达时 sync_long 的积累
相位不同，L-LTF 没落在期望窗口位置（ideal_lower_peak=171）→ 位置敏感的
候选搜索失败。**这是 sync_long 搜索的窗口相位敏感性，真实缺陷，非环境。**

**修复方向**：让搜索窗口对齐 wifi_start 标签位置（用标签的时序信息而非
纯边界驱动），或让 L-LTF 搜索位置宽容。但 P135 当年为激活多特征门而刻意
改为边界驱动，此处有设计张力——需充分理解 P135 动机后再动。

## 8. 三次取证终定（2026-08-10，p163e_fate.err）：never-searched

加搜索尝试点位置日志（Top-correlation 行带 tag_off）后逐帧三向 join
（episode / search / commit / seq）：

- **全部 19 个丢失帧 = 从未被搜索（never-searched）**——不是"搜索了但
  位置不合拒绝"。搜索一旦运行 3232/3232 全提交。
- 满强度帧被检测、episode 被转发，但 sync_long 的 SYNC_LENGTH 边界搜索
  没有覆盖其 L-LTF。

**机制终定**：P135 为激活 P133 多特征门把搜索从 tag 快路径改为**纯边界
驱动**（积累满 SYNC_LENGTH 才搜）。压缩流（sync_short 丢 SEARCH 样本）上
每个 episode 到达时 sync_long 的积累相位不同，~0.6% 帧的 L-LTF 错过搜索
窗口相位 → 无提交 → 链损。**这是 sync_long 搜索的窗口相位敏感性，真实
结构性缺陷，非环境。**

**修复方向（有风险）**：用 wifi_start 标签位置对齐搜索积累窗口（不绕过
P133 门，只改窗口相位）——但这是对最脆弱文件的时序改动，且 P135 边界
驱动是承重的（当年为激活门控）。**预期收益 ~0.5%（清轮），小于环境轮间
摆动（±1-2%）**——端到端改善会被摆动淹没。

## 9. 四次取证（2026-08-10，p163f_fate.err）：修正"never-searched"伪影

⚠️ **自我纠错**：第 8 节的"never-searched"结论是**仪表伪影**——
`d_last_wifi_start_tag_offset` 最初只在 SYNC-ignore 路径捕获，而 FAST_SYNC
（主导路径）没捕获 → 提交/搜索行 tag_off=0 → join 落空误判"无提交"。修正
（全路径捕获）后真相：

- **全部丢失帧都正常提交**（commit 参数 lower_peak/score 与 OK 帧同分布，
  无法区分）。
- 本运行 3197 帧：到达(EQ_TAG)=3195，DS=3190，终败 4。丢失 7 ≈ 4 解码终败
  + 3 提交后下游损（L-SIG/HT-SIG/均衡器尾）。
- **链损不是搜索失败，是"提交正常但下游失败"的信号级尾巴**。

**修正后的清轮残余预算（0.22%，本运行）**：~4 解码衰落尾 + ~3 对齐/下游尾。
两者都是硬尾巴。99.9%（≤3/3197）需把 7 压到 3。
