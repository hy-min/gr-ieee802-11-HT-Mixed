--b-len 1000 --b-interval 10 --tag sirpal_disc`（6 臂）

## 结论 1：判别成功 —— 是 **A 自身退化**，不是 B 缺席

`idx00 max` 给出关键组合：

```
b_life=125s (died=False)   ← B 全程在场，正常值
capture=546,698            ← 却低于正常（890k–1.03M）
```

**B 发射正常，是 A 的接收能力下降了。**

**⚠️ 由此推翻我自己的一个推断**：P190 里我从 `capture` 偏低推断
"**B 有效在场量不足**"——**方向错了**。本 phase 证明 `capture` 对**两种**失效模式都给低值：

| 失效模式 | 实例 | b_life | capture |
|---|---|---|---|
| B 缺席 | P189 idx02 | **55s** | 49,165 |
| **A 退化** | **P191 idx00** | **125s（正常）** | **546,698** |

⇒ **`capture` 是一台非特异性的异常检测器**：它能"标记坏臂"（用途成立），
但**不能单独判定原因**。**只有 `b_life` 与 `capture` 同时读才能分开两者**——
这正是本 phase 存在的理由。

## 结论 2：A=31.5 的**自身崩塌**是跨批次重复现象

崩塌的签名 = **臂内趋势 `trend = mean(后2窗)/mean(前2窗)` 远小于 1**。
把所有 A=31.5 **静默臂**（B 完全不在场）排出来：

| 批次（日期）| 逐窗 | trend |
|---|---|---|
| neargeo2（09-14）| `128 114 32 3 5` | **0.03** |
| sirpal_disc（09-18，本 phase）| `134 134 105 37 4` | **0.15** |
| sirpal_disc（09-18）| `111 42 24 26 23`（max 臂）| **0.32** |
| sirpal_315（09-18）| `136 133 108 117 52` | 0.63 |
| sirpal_315（09-18）| `131 127 128 124 92` | 0.84 |
| 其余 A=31.5 臂 | … | 0.95–1.23 |

**跨度 4 天、三种不同的 B 配置、全部出现在 B 缺席的静默臂上**
⇒ **与干扰无关，是 A 自身链路的间歇性失稳。**

对照：**其他所有工作点**（16/24/18/12/6/0 dB）的 trend 落在 **0.87–1.03**，
一条崩塌都没有。**该现象是 A=31.5 独有的。**

**本批次的崩塌率：6 臂里 4 臂崩塌**（trend ≤ 0.84）。
三条"配对"里 idx0（−25.1pp）与 idx2（+11.5pp）**都至少有一臂在退化**，
**没有一条能给出可信差值**——包括那个正号（干扰"改善"链路，物理上无意义）。

## 结论 3：第三类失效模式 —— B **启动过晚**

`idx01 max` 报 `INVALID: b_life=66s`，但 **`died=False`**——B 没有提前退出。

**根因**：受害机在固定 `--b-start-grace = 25s` 睡眠后即开始测量。
**那是一个任意超时**；若 B 的 UHD 初始化耗时更长，B 的发射就晚于测量窗开始。
本臂里 B 只覆盖了 66s，而受害机测量窗是 ~120s。

注意：**上一 phase 的修法（B 的 `--run` 240→900）治不了这一类**——
它杜绝的是"自然退出"，而这是"启动慢"。

### 修复：条件等待替换任意超时

```python
started, why = wait_interferer_started(
    outdir / f'idx{idx:02d}_interferer.out', b_proc)   # 轮询至首条 TX_LSIG_Original
```

「B 正在发射」从**被假设**变成**被验证**。（子进程 stdout 是块缓冲，但该日志
以 ~4.5 kB/帧 增长，新 TX 行在一秒内浮现。）

**门限随之调整**：`need_s = 0.75×(grace + run×windows)` → **`0.9×(warmup + run×windows)` = 85.5s**
（B 现在先于受害机启动，公式里不再需要 grace 项）。
相容性核对：历史正常臂 125–127s 全 PASS；P191 idx01（66s）与 P189 idx02（55s）正确判 INVALID。

## 门禁战绩（P190 清算的价值兑现）

本 phase 的 6 臂里，门禁连续抓到**两种不同失效**：

| 臂 | 判据 | 失效模式 |
|---|---|---|
| idx01 max | `b_life=66s` | B 启动过晚（**新模式**）|
| idx00 max | `capture=546,698`（未触发，高于 500k 门槛）| A 自身崩塌 |

⚠️ **idx00 暴露出门限过松**：capture 546,698 > 门槛 500,000，**该臂被判定为有效**，
但它显然在退化。正常下界是 890k，所以余量只有 1.78×。
**`trend` 对这类"臂内崩塌"更对症**（0.32 vs 健康 0.84–1.10）。

### 新增门：臂内崩塌（`collapse`）

```
collapse = (首窗 >= 80) 且 (末窗 < 0.4 × 首窗)
```

**为何不用裸 trend**：一个只看「后2窗/前2窗」的门会**误杀 A=0 的 max 臂**——
它的 trend 是 **0.00**（`[1,0,0,0,0]`），但那是全场**最可复现**的测量
（三次 0.0 / 0.0 / 0.1%）。**"均匀死透"与"中途猝死"的 trend 都接近 0**，
必须要求**起始是健康的**才能区分。

**标定（67 臂）**：触发 5 条，**全部是 A=31.5 的崩塌**；最低的健康臂首窗跌幅是
**0.63**，所以 0.4 这个系数两侧都留了余量。**A=0 的三个 max 臂经反例核对，全部正确保留。**

`trend=` 仍印在结果行里作为诊断（它对 0.4–0.84 之间的**轻度衰退**敏感但不判罪）。

### CAPTURE 门限收紧：500,000 → 700,000

新数据点暴露旧门过松：`P191 idx0 max` 的 capture **546,698 > 500,000**，
**被判定为有效**，但该臂明显在退化。收紧后到正常下界 1.2×、到最近坏臂 1.28×。

⚠️ **该门限只对当前 B 配置（len1000 / 10ms）标定过。** 普查发现
`2026-09-14 neargeo` 批次用的是**另一种配置**，其 max 臂 capture 只有
**38k–47k**，而那批**臂是好用的**（83.7% / 95.5%）。
**capture 随 B 帧长 × 速率缩放，改 `--b-len`/`--b-interval` 必须重新标定**——
否则会把整批好臂误杀。此警告已写入两处代码的帮助文本。

## 判定：A=31.5 不可用作定量工作点

理由不是"噪声大"，而是**它的臂多数根本测不出来**：本批 6 臂中 4 臂崩塌，
另 1 臂 B 启动过晚，**只有 1 臂（idx02 max）健康**。

**对主结论无损**：曲线由 A=24/18/12/6/0 五点支撑（各点 n=3，趋势全部 0.87–1.03）；
A=31.5 在曲线里只贡献"≈0"那一点，而它的三次健康测量（−5.8 / +7.9 / −2.6）
本就一致指向 ≈0，与捕获理论相符。

## 机制：未解决（诚实清单）

**A=31.5 为何会自发崩塌，机制未知。** 本 phase 只确立了"是什么"（A 自身退化、
与干扰无关、A=31.5 独有、间歇性）与"怎么测"（trend + b_life/capture 配对），
没有触及"为什么"。

**下一步的仪器已经找好并读过代码**（避免再造未标定仪器）：
`IEEE80211_LLTF_RESID_DUMP=1` → `[LLTF_RESID] rms= cfo= sfo=`，逐帧一行，
可检验"LO 热漂移导致累积 CFO"这一候选。（代码注释告警：实时下 `DECODE_*` 行
比 `RESID` 行晚约 100ms 到达，**按序配帧不可靠，只能看趋势**。）

**优先级判断：低。** 该工作点不在主曲线上；机制问题不阻塞任何结论。
